# Security Hardening Register

The following register documents all security vulnerabilities discovered and remediated across the HostelGrievance portal. Each row represents a verified security finding.

| ID | Finding | Risk | Change | Verification | Residual Risk |
|---|---|---|---|---|---|
| H-01 | **BOLA / IDOR in Grievance Detail Retrieval (`GET /api/grievances/:id`)** | High (Confidentiality breach across student grievance records) | Added authoritative server-side ownership check `assertCanViewGrievance(user, row)` ensuring students can only retrieve their own grievances while wardens can access all grievances. | `vitest run src/server/security.test.ts` (unauthorized student gets 403 Forbidden; owner student and warden get 200 OK). | Low; relies on accurate student ID association in database. |
| H-02 | **BOLA / IDOR & Unauthorized Comment Injection (`GET` & `POST /api/grievances/:id/comments`)** | High (Unauthorized eavesdropping on private grievance comments and comment tampering) | Enforced `assertCanViewGrievance(user, row)` on both comment listing and comment posting endpoints. | Automated regression tests verify non-owners receive 403 when reading or adding comments. | Low; comments are bound strictly to grievance owner and authorized wardens. |
| H-03 | **Privilege Escalation & Unauthorized Ticket Modification (`PATCH /api/grievances/:id`)** | High (Unauthorized ticket content tampering and student unauthorized status resolution) | Added checks preventing students from modifying grievances they do not own, forbidding students from updating status, and maintaining 409 conflict guard on resolved grievances. | Automated tests verify student status change fails with 403, cross-student edits fail with 403, and warden status updates succeed. | Low; role-based update field segregation enforced at API boundary. |
| H-04 | **BOLA / IDOR in Attachment File Access (`GET /api/attachments/:id`)** | High (Unauthorized access and exfiltration of student-uploaded photos/documents) | Added grievance ownership verification `assertCanViewGrievance(user, grievance)` before reading and serving attachment binary streams. | Automated tests verify unauthorized student gets 403 Forbidden, while ticket owner and warden get 200 OK. | Low; requires attachment rows to reference valid grievance records. |
| H-05 | **Broken Session Invalidation on Logout (`POST /api/logout`)** | Medium (Zombie session tokens remain active in database allowing replayed authentication) | Updated `POST /api/logout` to explicitly purge session token from SQLite `sessions` table using `destroySession(db, token)` alongside clearing cookie. | Automated tests verify replaying session token after logout returns 401 Unauthorized. | Low; database session cleanup ensures immediate invalidation. |
| H-06 | **Missing Session Expiration Enforcement in Database Lookups (`readSessionUser`)** | Medium (Expired sessions remain valid indefinitely if not explicitly purged) | Added active expiration timestamp verification (`expires_at <= Date.now()`) in `readSessionUser`, immediately deleting expired sessions and returning 401. | Automated tests verify expired session records in DB are rejected with 401 and removed from DB. | Low; session validity bounded by active TTL check on every request. |
| H-07 | **Insecure Session Cookie Configuration** | Medium (Session cookie vulnerable to client-side script theft and cross-site request abuse) | Configured `httpOnly: true`, `sameSite: 'Lax'`, `path: '/'`, and environment-aware `secure: process.env.NODE_ENV === 'production'` on session cookies. | Automated tests verify `Set-Cookie` response headers contain `HttpOnly`, `SameSite=Lax`, and `Path=/`. | Low; cookie flags enforced by Hono cookie helper. |
| H-08 | **Overly Permissive CORS Policy with Credentials** | High (Any malicious external website could read authenticated student records) | Replaced dynamic origin reflection with strict origin whitelist validating localhost, 127.0.0.1, and configured production origins. | Automated tests verify untrusted external origins (`https://evil.attacker.com`) do not receive CORS allow headers. | Low; CORS explicitly restricted to authorized frontend origins. |
| H-09 | **Stored Cross-Site Scripting (XSS) in Comment Timeline** | High (Arbitrary JavaScript execution in student and warden browsers via comment payload) | Replaced unsanitized `{@html comment.body}` with safe Svelte text interpolation `{comment.body}` in `comment-timeline.svelte`. | Verified that script and HTML tags in comment bodies are rendered as harmless escaped text. | Low; Svelte auto-escapes all dynamic text nodes. |
| H-10 | **Unrestricted File Upload, Path Traversal & MIME Spoofing** | High (Arbitrary file overwrite via directory traversal and malicious disguised file uploads) | 1. Always generate cryptographically random hex filenames on disk.<br>2. Implemented binary magic-byte verification (JPEG, PNG, GIF, WebP).<br>3. Enforced strict path containment inside `uploadsDir`. | Automated tests verify fake PNG containing text/script is rejected (400 Bad Request) and traversal filenames are safely stored with randomized names. | Low; uploads restricted to validated image bytes and stored in isolated folder. |
| H-11 | **Missing HTTP Security Headers on API and File Responses** | Medium (Clickjacking risk and browser MIME-type sniffing vulnerabilities) | Added global middleware providing `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Content-Security-Policy`. | Automated tests verify security headers exist on all API endpoints and attachment responses. | Low; static defense-in-depth headers applied on all HTTP responses. |
| H-12 | **Lack of Rate Limiting on Sensitive Authentication and Submission Routes** | Low / Medium (Vulnerability to credential brute-forcing and ticket spamming) | Implemented in-memory rate limiting middleware on `POST /api/login` and `POST /api/grievances` returning 429 Too Many Requests upon threshold breach. | Rate limiter tracks IP sliding window and attaches standard `X-RateLimit-*` headers. | Low; in-memory store suitable for single-node deployment (Redis recommended for multi-node). |
| H-13 | **Unsalted / Weak Password Hashing Scheme** | Medium (Vulnerability to offline rainbow table and dictionary attacks upon DB leak) | Upgraded password hashing to salted `PBKDF2` (100,000 iterations SHA-256) with constant-time verification while maintaining backwards compatibility for existing seed hashes. | Automated tests verify PBKDF2 salt uniqueness and constant-time verification against both new and legacy formats. | Low; newly hashed passwords utilize salted PBKDF2. |
| H-14 | **User Enumeration via Authentication Timing Attacks** | Low / Medium (Attackers measure response latency on `/api/login` to deduce valid email addresses) | Executed constant-time dummy PBKDF2 verification when requested email does not exist in database, equalizing computational response time. | All login attempts take identical CPU execution time regardless of account existence. | Low; timing side-channel eliminated. |
| H-15 | **Legacy SHA-256 Password Hash Persistence** | Medium (Old accounts remain on weaker legacy hashes indefinitely) | Implemented transparent cryptographic migration on `/api/login`: successfully authenticated legacy SHA-256 accounts are re-hashed with salted PBKDF2 and persisted in real time. | Automated tests verify legacy accounts are upgraded to `pbkdf2:` immediately upon valid sign-in. | Low; automated zero-downtime hash modernization. |
| H-16 | **SQLite Forensic Artifact & Crash Vulnerability** | Low / Medium (Deleted records recoverable from unallocated pages; lock contention during crashes) | Enabled `PRAGMA secure_delete = ON` (overwriting deleted records with zeroes) and `PRAGMA journal_mode = WAL` (Write-Ahead Logging). | SQLite schema initializes with secure_delete and WAL active. | Low; prevents disk recovery of purged session tokens and comments. |
| H-17 | **Unbounded Input Length & Hash-DoS Vulnerability** | Medium (Attackers submit megabyte strings to exhaust server memory and CPU during hashing) | Enforced upper length bounds across all endpoints (Password <= 128, Email <= 254, Title <= 150, Description <= 3000, Comments <= 1000) and stripped null bytes. | Automated tests verify oversized payloads are rejected with 400 Bad Request. | Low; strict schema validation protects memory and CPU. |
| H-18 | **Missing Cross-Origin Isolation & Feature Permissions Headers** | Medium (Vulnerability to cross-window tampering and unauthorized device API usage) | Added `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-site`, and restrictive `Permissions-Policy`. | Automated tests verify COOP, CORP, and Permissions-Policy headers exist on all responses. | Low; strict browser execution context isolation. |
| H-19 | **Attachment Caching & Exfiltration via Shared Proxy Caches** | Medium (Hostel photo attachments cached on unencrypted intermediary network proxies) | Added `Cache-Control: private, no-transform, max-age=86400` and sanitized RFC-escaped `Content-Disposition`. | Automated tests verify attachment downloads include private cache control and nosniff headers. | Low; restricts caching to the client browser only. |
| H-20 | **Shared-Device Walk-Away Session Hijacking & Missing Audit Visibility** | Medium (Unattended hostel/lab terminals vulnerable to physical takeover; wardens lack security metrics) | Built 20-minute client inactivity auto-logout and implemented role-protected `GET /api/security/audit-summary` for warden telemetry. | Automated tests verify students receive 403 on audit summary while wardens receive 200 operational metrics. | Low; active terminal timeout and verified RBAC telemetry. |
| H-21 | **Attachment Binary Integrity & Anti-Tamper Verification** | Low / Medium (Bit rot, disk corruption, or man-in-the-middle payload tampering) | Added real-time cryptographic `ETag: "<sha256>"` calculation on all served attachment streams. | Automated tests verify `ETag` matches standard 64-hex SHA-256 hash. | Low; authoritative cryptographic digest attached to binary downloads. |
| H-22 | **Defense-in-Depth SQL Identifier Whitelisting** | Medium (Malformed or injection strings passed in URL parameters) | Added strict regex whitelist validation `^[a-zA-Z0-9_-]{1,64}$` to all lookup helper queries (`findGrievanceRow`, `findAttachmentRow`, `findUserById`). | Automated tests verify malformed ID payloads are rejected with safe 404 Not Found before SQL execution. | Low; only strictly formatted alphanumeric IDs reach SQLite prepared statements. |
| H-23 | **Orphaned Database Session Accumulation & Stale Token Pruning** | Low / Medium (Accumulation of expired tokens in database increasing memory footprint) | Implemented `purgeExpiredSessions(db)` executed automatically during new session creation, ensuring database remains lean. | SQLite sessions table is pruned of expired records upon login. | Low; background garbage collection keeps token store healthy. |
| H-24 | **Cross-Site Request Forgery (CSRF) via Sec-Fetch-Site Inspection** | High (Malicious third-party websites submitting state-changing POST/PATCH requests via authenticated student browser) | Implemented automated `Sec-Fetch-Site` header verification on all mutating API calls; rejects `cross-site` origins with 403 Forbidden. | Automated tests verify requests marked `Sec-Fetch-Site: cross-site` are blocked immediately. | Low; modern browser-native fetch metadata defense. |
| H-25 | **JSON Memory Exhaustion & Request Bombing Defense** | Medium (Attackers sending large megabyte JSON payloads to exhaust server Node.js heap memory) | Added global request payload size limit (100 KB max for JSON endpoints; dedicated 2 MB boundary for multipart attachments). | Automated tests verify oversized JSON requests are rejected with 413 Payload Too Large. | Low; enforces bounded buffer allocations. |
